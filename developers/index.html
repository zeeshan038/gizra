Restaurant Integration API

Connect an external POS or kitchen display system to GIZRA. Pull orders placed on GIZRA into your own system, and push kitchen progress back so the customer sees accurate status.

Overview

The integration is two-directional and deliberately small:

  1. GIZRA → your POS. You read orders from the orders endpoints.
  2. Your POS → GIZRA. You post status changes as the kitchen works: accepted, cooking, ready, delivered, cancelled.

Everything else — menu, pricing, payments, courier assignment, payouts — stays in GIZRA. You do not need to mirror it.

Two integration paths, and two ways to authenticate:

1. Polling with your account token — call GET /api/v1/vendor/current-orders every 10–30 seconds and diff against what you have already imported. Fastest way to start testing, no setup required beyond logging in.

2. Scoped partner key + webhooks — recommended for production. A partner API key is scoped, revocable, and never exposes the restaurant's password; webhooks push order events to you instead of polling. Both are live today. Contact GIZRA integrations to have a key issued and a webhook endpoint registered — see those sections for exact headers and payloads.

Quick start

1. Get a token

curl -X POST https://backend.gizra.app/api/v1/auth/vendor/login \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"email":"restaurant@example.com","password":"YOUR_PASSWORD"}'
{ "token": "t3hmpZFAlLLqDFVqLjdR5PId…", "is_phone_verified": true }

2. Read the active orders

curl https://backend.gizra.app/api/v1/vendor/current-orders \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/json" \
  -H "X-localization: he"

Returns a bare JSON array. Anything with "order_status": "pending" is waiting for the restaurant to accept it.

3. Accept it and start cooking

# accept
curl -X POST https://backend.gizra.app/api/v1/vendor/update-order-status \
  -H "Authorization: Bearer $TOKEN" \
  -F "_method=put" -F "order_id=100152" -F "status=confirmed"

# start cooking, promise 20 minutes
curl -X POST https://backend.gizra.app/api/v1/vendor/update-order-status \
  -H "Authorization: Bearer $TOKEN" \
  -F "_method=put" -F "order_id=100152" -F "status=processing" -F "processing_time=20"

That is a complete working integration. The rest of this page is detail.

Authentication

HTTP bearer token. Obtain it once from the login endpoint and reuse it; there is no fixed expiry. Send these headers on every request:

Authorization: Bearer <token>
Accept: application/json
X-localization: he
HeaderRequiredPurpose
AuthorizationYesBearer token from login.
AcceptYesAlways application/json.
X-localizationNoLanguage of returned messages: en, he, ar, es, bn. Does not change data.

The token is currently obtained with the restaurant's own account password. That means whoever holds the token can do anything the restaurant can do in the GIZRA vendor app.

Treat it as a full credential regardless: it lives on your server, never in a browser bundle, mobile app, or any binary a third party can unpack. Scoped partner keys are live and avoid this exposure entirely — recommended over the account token for any production integration.

Security requirements

These are conditions of using the integration, not suggestions.

RuleWhy
Store the token server-side onlyA token in client code is a published token. Anyone who extracts it can read every order and change every status.
Never put the token in a URL or query stringQuery strings are written to web server logs, proxy logs and browser history.
TLS 1.2+ for every callPlain HTTP is refused.
One credential per restaurantNever share one token across multiple restaurants. Compromise then affects one site, not all of them.
Do not log full request or response bodies in productionOrder payloads contain customer name, phone, email and street address. Log identifiers, not contents.
Rotate on staff change or suspected exposureChange the restaurant password and log in again. This invalidates the old path to a token.
Back off on errorsOn a 5xx or a network failure, retry with exponential backoff. Do not hammer at the poll interval.
Handle the same order arriving twiceKey on id. Polling and, later, webhook retries can both re-deliver an order you have already seen.

Never expose GIZRA credentials through your own public API or front end. If your POS has a web dashboard, it must call your server, and your server calls GIZRA. Proxying the token to a browser defeats every control above.

Pulling orders

GET/api/v1/vendor/current-ordersLive

Every order that is not finished: pending, accepted, confirmed, processing, handover, picked_up. This is the endpoint you poll.

Returns a bare JSON array, not an object envelope.

GET/api/v1/vendor/order-details?order_id=100152Live

The line items — what the kitchen actually makes, with variations and add-ons. The array sits at order.details in the response.

GET/api/v1/vendor/order?order_id=100152Live

A single order header. Cheaper than re-pulling the whole active list when you only need to re-check one order.

GET/api/v1/vendor/completed-ordersLive

Finished orders, paginated.

QueryTypeNotes
statusstringall, delivered, refunded, canceled, failed
offsetinteger1-based page number, not a row offset. Page 2 is offset=2.
limitintegerRows per page. 10 is typical.
GET/api/v1/configLive

No auth required. Read once at startup and cache. Gives you currency_symbol, timeformat, order_confirmation_model and order_delivery_verification — the last one tells you whether delivered needs an OTP.

Pushing status

POST/api/v1/vendor/update-order-statusLive

The single endpoint for all kitchen progress.

Two format details that trip people up:

1. The body is multipart/form-data, not JSON. The endpoint optionally accepts delivery proof images, so it takes a multipart body for every call.

2. It is a POST that carries a field _method with the literal value put. This is Laravel method spoofing. Send it or the request is rejected.

Order lifecycle

pending→ confirmed→ processing→ handover→ picked_up→ delivered
StatusWho sets itMeaning
pendingCustomerOrder placed, waiting for the restaurant. This is your trigger to print and alert.
acceptedPlatformOnly appears when the platform is configured for deliveryman confirmation.
confirmedYouRestaurant accepted the order.
processingYouKitchen is cooking. processing_time holds the promised minutes.
handoverYouFood is ready and handed to the courier.
picked_upCourierOn the way to the customer. Read-only for you.
deliveredCourier, or you for self-deliveryCompleted.
canceledYou, customer or adminYou may cancel only while pending, and only if the platform permits it.
failedPlatformPayment or fulfilment failed.
refund_requested / refundedPlatformRefund flow. Read-only for you.

Each status also has a matching timestamp field on the order (pending, confirmed, processing, handover, delivered, canceled…). A null means that step has not happened.

Two variation formats exist for historical reasons. Newer records use variation[].values[].label. Older ones use a flat array with type and price. Handle both: if values is absent, read type.

Webhooks Live

Registration is admin-panel-only. Contact GIZRA integrations with the HTTPS endpoint you want events sent to and which events you want (order.created, order.status_changed). There is no self-service registration API. You'll be given a signing_secret once, at registration time.

GIZRA POSTs order events to your registered HTTPS endpoint as they happen, removing the need to poll.

Every delivery carries:

Content-Type: application/json
X-Gizra-Event: order.created
X-Gizra-Delivery: 8f14e45f-ea2b-4c1a-9d0e-1c2b3a4d5e6f
X-Gizra-Timestamp: 1754130741
X-Gizra-Signature: sha256=<hex>

Body:

{
  "event": "order.created",
  "delivery_id": "8f14e45f-ea2b-4c1a-9d0e-1c2b3a4d5e6f",
  "created_at": "2026-08-02T07:32:21+00:00",
  "data": {
    "order_id": 100152,
    "restaurant_id": 3,
    "order_status": "confirmed",
    "order_amount": 53.45,
    "payment_method": "cash_on_delivery"
  }
}

Only two events are emitted: order.created when the restaurant confirms a new order, and order.status_changed for every subsequent transition — including cancellations, which arrive as order.status_changed with data.order_status: "canceled", not a separate event type. For the full order object, fetch it with data.order_id against the orders endpoints (webhook payloads carry identifiers, not the full order, to keep deliveries small).

Verifying a delivery

In this order, and reject at the first failure:

  1. Reject if X-Gizra-Timestamp is more than 300 seconds from your clock. This blocks replay of an old capture.
  2. Compute HMAC-SHA256(signing_secret, timestamp + "." + raw_body) over the raw body, before any JSON parsing, and compare with a constant-time function.
  3. Reject if you have already processed this X-Gizra-Delivery id. Retries repeat it.
  4. Return 2xx within 5 seconds. Queue the work; do not do it inline.
// Node.js
const crypto = require('crypto');

function verify(req, secret) {
  const ts  = req.get('X-Gizra-Timestamp');
  const sig = req.get('X-Gizra-Signature') || '';

  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return false;

  const expected = 'sha256=' + crypto
    .createHmac('sha256', secret)
    .update(ts + '.' + req.rawBody)   // rawBody, not the parsed object
    .digest('hex');

  const a = Buffer.from(sig), b = Buffer.from(expected);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
<?php
// PHP
function gizra_verify(string $raw, string $ts, string $sig, string $secret): bool {
    if (abs(time() - (int)$ts) > 300) return false;
    $expected = 'sha256=' . hash_hmac('sha256', $ts . '.' . $raw, $secret);
    return hash_equals($expected, $sig);
}

Non-2xx responses are retried with exponential backoff for up to 24 hours, after which the webhook is automatically disabled — check in with GIZRA if deliveries stop arriving.

Partner API keys Live

Issued from the GIZRA admin panel, bound to one restaurant. Contact GIZRA integrations with the restaurant, the scopes you need, and optionally an IP allowlist. The secret is shown once at creation and never again — if it's lost, ask GIZRA to issue a new key and revoke the old one.

Today's account-token auth (above) grants everything the restaurant can do. Partner keys are the scoped alternative, recommended for any production integration:

  • Scoped — orders:read, orders:write, menu:read. A read-only POS never gets write access.
  • Bound to one restaurant — a leaked key cannot reach another restaurant's orders.
  • Revocable — cut a single integrator off without changing the restaurant's password.
  • Optionally IP-restricted — accepted only from the partner's server addresses.
  • Request-signed — X-Gizra-Key plus an X-Gizra-Signature HMAC, so a captured request cannot be replayed.
  • Rate-limited independently — 120 requests/minute for reads, 60/minute for writes, per key. A 429 with Retry-After means back off.

Authenticating a request

Every call needs three headers instead of one bearer token:

X-Gizra-Key: gzk_xxxxxxxxxxxxxxxxxxxxxxxx
X-Gizra-Timestamp: 1754130741
X-Gizra-Signature: sha256=<hex>
Accept: application/json

X-Gizra-Signature is HMAC-SHA256(secret, timestamp + "." + raw_body), hex-encoded, prefixed with sha256= — the same scheme as webhook verification above, just computed by you instead of GIZRA. For a GET request the raw body is empty, so you're signing "<timestamp>.". The request is rejected if the timestamp is more than 300 seconds from GIZRA's clock.

// Node.js — signing a GET request
const crypto = require('crypto');

const ts = Math.floor(Date.now() / 1000).toString();
const sig = 'sha256=' + crypto.createHmac('sha256', secret).update(ts + '.').digest('hex');

fetch('https://backend.gizra.app/api/v1/partner/current-orders', {
  headers: {
    'Accept': 'application/json',
    'X-Gizra-Key': keyId,
    'X-Gizra-Timestamp': ts,
    'X-Gizra-Signature': sig
  }
});
<?php
// PHP — signing a GET request
$ts  = (string) time();
$sig = 'sha256=' . hash_hmac('sha256', $ts . '.', $secret);

$ch = curl_init('https://backend.gizra.app/api/v1/partner/current-orders');
curl_setopt($ch, CURLOPT_HTTPHEADER, [
    'Accept: application/json',
    "X-Gizra-Key: $keyId",
    "X-Gizra-Timestamp: $ts",
    "X-Gizra-Signature: $sig",
]);
curl_setopt($ch, CURLOPT_RETURNTRANSFER, true);
$response = curl_exec($ch);

Signing update-order-status is the same scheme over the raw multipart body — build the multipart payload first (with its actual boundary), then sign those exact bytes as timestamp + "." + raw_multipart_body. Signing the logical field values instead of the serialized bytes is the most common mistake here and will fail verification.

Why this matters for existing installs

Partner keys are a server-side-only addition. No restaurant needs to update or reinstall the GIZRA app, and the existing account-token authentication above keeps working unchanged — use whichever fits your integration; they are not mutually exclusive.

Support

For access, a test restaurant account, or to report a discrepancy between this document and the API's behaviour, contact GIZRA integrations. Include the endpoint, the full request minus credentials, the response body and the timestamp.

When reporting a problem, the id of an affected order makes it far faster to trace.
